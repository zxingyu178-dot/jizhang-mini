## 1. 备份链路

### 1.1 格式与兼容

| 项 | 内容 |
| --- | --- |
| 当前格式 | `{ format:'daily-value-mini-backup', schemaVersion:3, ... }` |
| 当前版本 | `SCHEMA_VERSION = 3` |
| 可恢复版本 | `SUPPORTED_SCHEMA_VERSIONS = [1, 2, 3]` |
| 恢复时归一 | 不管原始是 V1 / V2 / V3，恢复后统一为 **V3** |

**用户视角的大白话**：以前版本（V1、V2）备份出来的文件，在有新版本 App 上**照样能恢复**，不会被拒。

### 1.2 本轮的关键改动：老备份不再被误判

**问题**：老版本备份文件里**没有 `createdAt` 这个字段**（那时候还没这个字段）。原来代码分不清两种情况：

1. 老备份"本来就没这个字段" ← **正常，不该报错**
2. 文件里"有这个字段但值是坏的" ← **真问题，该报错**

两种情况混在一起判，结果就是：**老备份的正常恢复被当成异常拦下来了**。

**现在的处理**：

| 情况 | 判定 | 行为 |
| --- | --- | --- |
| 字段完全没给（无该字段 / `undefined` / `null`） | **老备份的正常情况** | 静默补齐为当前时间，**不报错、不弹窗、不打扰用户** |
| 字段存在但**值非法**（不是合法时间） | **真问题** | 保留**可查诊断**（字段名 + 错误码），让人能定位到是哪个字段坏了 |
| 字段存在且值合法 | 正常 | 逐字段比对，**不跳过任何字段** |

**为什么这很重要**：用户手上有几年前的备份，想换手机恢复。如果因为一个"当年还不存在的字段"被判成异常，用户会以为**备份废了** —— 实际数据是好的。这类误判对用户的打击比真出错还大。

### 1.3 备份恢复后统计一致性

**问题**：恢复完账本条数对了，但**统计数字对不上**（比如花了多少钱不一致），用户会更慌。

**做法**：`tests/backup-restore-statistics.test.js` 专项验证恢复前后**统计结果一致**，本版 **44 项通过**。

## 2. 恢复链路

### 2.1 三个曾经的真实风险（第一阶段已修）

| 风险 | 原来会怎样 | 现在怎么防 |
| --- | --- | --- |
| **删除失败被忽略** | 删旧月份文件失败，代码不看返回值继续写 → 出现"新账单 + 旧账单"**叠加**，条数校验还可能恰好通过 | `fs.removeStrict()` **fail-closed**：删不掉就是失败，**在写入新账单之前就中止** |
| **安全点结构没校验** | 拿一个残缺的安全点去回滚 → 等于用坏数据覆盖好数据 | 删除前先做完整结构与语义校验，不合格**一个文件都不动** |
| **恢复后只查数量不查集合** | 条数一样但**内容不同**也算通过 | 回读比对 **数量 + ID 集合 + 关键字段签名 + 重复 ID** |

### 2.2 恢复的标准动作顺序

```
① 校验备份文件（格式 / schemaVersion / 语义）
② 生成安全点（保存当前完整状态）
③ 校验安全点（结构 + 语义，不合格就停，不动任何文件）
④ 按月份分组，只删除「目标月份之外」的分片（每个月严格确认删除成功）
⑤ 目标月份用 writeMonthFile 原子覆盖（不依赖 unlink，不会与旧账单叠加）
⑥ 严格回读对账：数量 / ID 集合 / 关键字段 / 重复 ID
⑦ 对账不过 → 自动回滚；回滚结果如实报告
```

**关键设计**：第 ④ 步"只删目标月份之外的分片" + 第 ⑤ 步"目标月份原子覆盖"，两者配合的效果是 —— **任何时刻都不会出现旧数据和新数据叠在一起**。即使某个多余月份删不掉，也会在写成新数据之前中止。

### 2.3 对账查什么（关键字段清单）

比对以下字段组成的签名，避免"条数对但内容错"：

`id` / `type` / `amountCents` / `occurredAt` / `categoryId` / `ledgerImpact` / `sourceTxnId` / `title` / `merchant` / `note` / `dailyValue.startDate` / `recurringRuleId`

签名用 `JSON.stringify([...])` 生成，**避免分隔符碰撞**（比如分类名里恰好有 `|` 这种字符时，朴素拼接会撞车）。

另外**元数据也一并核对**：分类文件必须是数组且条数一致、设置文件必须是对象、周期规则必须是数组且条数一致。

### 2.4 恢复失败时用户看到什么（四级提示，不误导）

| 提示级别 | 含义 | 用户该怎么做 |
| --- | --- | --- |
| **未修改** | 恢复根本没开始执行，账本原样没动 | 可以直接重试 / 换个备份文件 |
| **已恢复** | 恢复成功，且对账通过 | 正常使用 |
| **恢复未完成** | 中途失败，已自动回滚 | 看一眼回滚结果（见下） |
| **无法确认** | 既没确认成功也没确认失败 | **不要继续操作**，先看备份文件是否还在 |

**为什么分四级**：最怕的是"糊里糊涂说失败/说成功"。分清楚用户才知道下一步干什么。

## 3. 回滚链路

### 3.1 核心原则：**不许谎报成功**

回滚过程中任何一步写入失败（月份 / 分类 / 设置 / 周期规则），错误对象里都带：

- `rollbackAttempted = true`
- `rollbackCompleted = **false**`
- `rollbackError.code`（具体失败码）
- **安全点始终保留**（不删，留作下次尝试或人工补救）

**原来会怎样**：写失败也报 `rollbackCompleted = true`，用户以为数据回来了，实际账本处于半截状态。**这是最危险的一种"假成功"**，本版彻底杜绝。

### 3.2 回滚失败后阻止重复提交

回滚失败 → **不允许再次提交恢复操作**。原因：账本已经处于不确定状态，再提交一次只会把情况弄得更乱。必须先确认状态。

### 3.3 错误码汇总（出问题时照着查）

| 错误码 | 含义 | 用户影响 |
| --- | --- | --- |
| `RESTORE_DELETE_FAILED` | 恢复时多余月份删除失败，已中止写入 | 账本未变，可重试 |
| `RESTORE_INTEGRITY_FAILED` | 恢复后账单集合 / 字段对账不一致 | 已自动回滚 |
| `RESTORE_META_INTEGRITY_FAILED` | 恢复后分类 / 设置 / 周期规则不一致 | 已自动回滚 |
| `ROLLBACK_SAFETY_UNAVAILABLE` | 安全点不可读（JSON 损坏 / 文件缺失） | 不动任何文件 |
| `ROLLBACK_SAFETY_INVALID` | 安全点结构 / 语义不合格 | 不动任何文件 |
| `ROLLBACK_DELETE_FAILED` | 回滚时多余月份删除失败 | 部分回滚，安全点保留 |
| `ROLLBACK_INTEGRITY_FAILED` | 回滚后账单对账不一致 | 安全点保留 |
| `ROLLBACK_META_INTEGRITY_FAILED` | 回滚后元数据核对不一致 | 安全点保留 |
| `MONTH_DELETE_FAILED` | 单个月份分片严格删除失败（底层） | 上游转成上面的码 |
| `FILE_DELETE_FAILED` | 文件严格删除失败（底层） | 上游转成上面的码 |

**共同点**：**每一条都是"看得懂、查得到"的**，没有一条是"出错了但不知道哪错"。

## 4. 安全点链路

### 4.1 什么是"安全点"（给非技术的解释）

**安全点 = 动手之前的照片**。恢复/回滚要动用户的账本，动之前先把当前完整状态存一份。万一动坏了，就照这张照片恢复回去。

所以安全点本身**必须可靠** —— 拿一张残缺的照片去恢复，比不恢复更糟。

### 4.2 校验清单（任何删除动作之前必做）

| 检查项 | 不合格时 |
| --- | --- |
| envelope：`format`、`schemaVersion` | `ROLLBACK_SAFETY_INVALID` |
| `data` 对象存在 | 同上 |
| `bills` 必须是数组 | 同上 |
| 每条 bill 必须是对象、必须有非空字符串 `id` | 同上 |
| Bill ID 不得重复 | 同上 |
| `categories` 必须是数组 | 同上 |
| `settings` 必须是对象 | 同上 |
| `recurringRules` 如存在必须是数组 | 同上 |
| 复用 `backupValidator.validateBackupRaw()` 做语义校验 | 同上 |
| 安全点文件读不出来（JSON 损坏 / 文件缺失） | `ROLLBACK_SAFETY_UNAVAILABLE` |

**两类错误都不删除任何当前文件、不删除安全点** —— 出事时"什么都不做"往往比"努力做点什么"安全。

### 4.3 本轮改动：临时安全点清理可诊断

| 项 | 改动 |
| --- | --- |
| 原始安全点 vs 临时安全点 | **隔离存放**，互不覆盖 |
| 回滚成功后 | 清理临时安全点 |
| 回滚失败后 | **两者都保留**（留证据，也留后路） |
| 清理失败 | 原来只有一句布尔结果；现在留**可查的错误码与字段名**，能看出是"文件删不掉"还是"根本没建" |

**为什么清理失败也要记**：临时安全点留在用户手机上会占存储，一直清不掉会累积。没有诊断信息就只能看着它堆，查不出原因。

## 7. 诚实声明：自动化覆盖不到什么

| 项 | 状态 | 说明 |
| --- | --- | --- |
| 真机上真的备份 → 删除数据 → 恢复这一整条链路 | **未执行** | 自动化用测试替身模拟文件系统；**真机要客户按 `docs/10_DEVICE_ACCEPTANCE.md` 第 6 节手工走一遍** |
| 真机上"恢复失败 → 自动回滚"的可视化提示 | **未执行** | 同上 |
| iOS / Android 系统级存储差异（微信本地文件系统在两端的表现） | **未在真机验证** | 自动化跑在 Node 环境，模拟不了真机文件系统行为 |
| 超大备份文件（例如几万笔）在真机上的恢复耗时 | **未实测** | 本轮性能测试只覆盖**导入预览**，未覆盖恢复耗时 |

**这四条必须说清楚**：自动化全绿 ≠ 真机上一定没问题。
本地文件系统的真实行为（权限、配额、读写失败形态）只有真机能验。
所以**真机验收不是走形式，是必做项** —— 尤其"备份→恢复→回滚"这一段。
