# v1.4.1 Gate 2 · 导入去重性能报告

- 目标：不改变去重规则，把 3,000 行导入预览在 30,000 笔账本下的中位耗时压到 **≤1,500 ms**，并争取 ≥2 倍提升。
- 改动文件：`packages/importer/core/dedupe.js`
- 新增测试：`tests/dedupe-index.test.js`（新旧算法差分）
- 测量工具：`tests/perf/dedupe.perf.js`（5 轮中位）

---

## 1. 优化内容

原实现（v1.4.0）：

- `findSuspect(b, existing)` 对每条新账单 `existing.some(...)` 全量扫描；
- `conservativeCsvMatch(b, existing)` 同样全量 `filter`；
- 工作量近似 O(新账单数 × 账本条数)。

现实现（一次性建索引后复用）：

| 索引 | 键 | 用途 |
| --- | --- | --- |
| A 精确流水号 | `source:sourceTxnId`（Set + Map） | existing / merge（语义不变） |
| B fingerprint | `makeFingerprint()`（Set） | 无流水号去重 |
| C 疑似重复 | `type|amountCents → 5 分钟时间桶 → bills[]` | 每条新账单只看当前桶 ±1 桶 |
| D CSV 日价补全 | `type|amount|category|note|分钟 → 无 id 账单[]` | 保留 zero / one / many |

语义保护：

- 索引只缩小候选集，最终仍执行原 `isSuspect()`：金额、时间窗口 `> TIME_WINDOW`、商户精确/包含、来源不同，条件逐条保持；
- 时间桶边界：桶宽 = 5 分钟，检查 `k-1 / k / k+1`，正好 5 分钟仍命中；
- 无效时间戳安全回退：新账单扫描该 `type+amount` 的全部桶，既有无效时间账单始终参与判断；CSV 分钟索引对无效时间直接返回 `zero`（与 `sameMinute(NaN,NaN) === false` 一致）；
- `suspect` 仍然只标记，不自动删除 / 合并；
- `skipped` 原样返回，不进入批次索引。

## 2. 新旧算法一致性

`tests/dedupe-index.test.js` 在文件内保留旧 `classify()` 作为 reference oracle，逐字段比较 `status / statusReason / existingId / mergePatch / 数量 / 顺序`。

覆盖：

1. 流水号精确重复；
2. 文件内部重复；
3. fingerprint 重复；
4. 5 分钟以内疑似重复；
5. 正好 5 分钟边界；
6. 超过 5 分钟；
7. 商户相同；
8. 商户包含关系；
9. 不同来源；
10. 相同来源；
11. 空商户；
12. CSV 唯一匹配；
13. CSV 多条匹配；
14. 日价补充；
15. 标题补充；
16. skipped；
17. 无效时间戳回退。

另加：

- 固定种子随机差分 30 组（每组最多 180 条账本 / 120 条导入，混合流水号、CSV、无效时间、skipped）；
- 极端分布：相同金额 + 相同时间桶 200 条账本 × 100 条导入；全部无效时间戳 50 条账本。

```

```

`tests/importer.test.js` 回归：`144 passed, 0 failed`。

## 3. 性能结果（同一台机器、同一数据、5 轮中位）

环境：AMD Ryzen 7 5800H / win32 10.0.26200 / Node v24.22.1 / 内存 FS / 3,000 行支付宝 CSV。

### 3.1 总耗时

| 账本规模 | 改前（Gate 0） | 改后 | 提升 |
| --- | --- | --- | --- |
| 5,000 | 221.9 ms | **27.8 ms** | 8.0× |
| 15,000 | 353.5 ms | **52.9 ms** | 6.7× |
| 30,000 | **1,618.2 ms** | **96.7 ms** | **16.7×** |

> 30k 档目标 ≤1,500 ms、至少 2×：**均达成**（96.7 ms，16.7×）。

### 3.2 分阶段（改后）

| 账本规模 | parse | adapt | validate | dedupe | 合计 |
| --- | --- | --- | --- | --- | --- |
| 5,000 | 4.1 ms | 7.7 ms | 0.3 ms | 15.7 ms | 27.8 ms |
| 15,000 | 2.2 ms | 7.3 ms | 0.4 ms | 43.0 ms | 52.9 ms |
| 30,000 | 1.9 ms | 7.5 ms | 0.3 ms | 87.0 ms | 96.7 ms |

### 3.3 索引自身

| 账本规模 | 索引构建 | classify 主体 | 桶数 | 平均桶大小 | 最大桶 | 候选检查次数 |
| --- | --- | --- | --- | --- | --- | --- |
| 5,000 | 11 ms | 2 ms | 5,000 | 1 | 1 | 0 |
| 15,000 | 58 ms | 2 ms | 15,000 | 1 | 1 | 0 |
| 30,000 | 86 ms | 2 ms | 30,000 | 1 | 1 | 0 |

说明：

- 本次导入数据是「3 年前后的历史账本 vs 2026-10 的 CSV」，`type + amount + 5 分钟窗口` 无重叠，所以候选检查为 0；这正是旧算法最吃亏、新算法收益最大的场景。
- 极端重叠场景（同金额 + 同 5 分钟桶 200 条）由 `dedupe-index.test.js` 验证**结果正确**；该场景下候选集必然变大，耗时会随桶大小线性增长，属索引方案的已知上界。
- 内存：Node `heapUsed` 采样抖动很大（本次出现 −16 MB / +100 MB 的不可信值），**不作为结论**。结构本身为 O(账本条数) 的 Map + 数组，30k 账本对应 30k 个单元素桶，无额外大缓冲区。

---

## 4. 结论

- 去重规则、用户确认机制、zero/one/many 语义均未改变；新旧算法在固定用例 + 30 组随机差分 + 极端分布下结果完全一致。
- 30,000 笔账本、3,000 行导入的预览耗时从 **1,618 ms → 96.7 ms**，满足 ≤1,500 ms 且超过 2 倍目标。
- 本报告全部为 Node + 内存 FS 数据，**不代表真机导入耗时**；真机仍受文件 I/O、`setData`、渲染影响，列入 Gate 5 真机验收。
