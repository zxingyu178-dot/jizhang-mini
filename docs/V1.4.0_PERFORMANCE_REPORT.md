# v1.4.0 Gate 5 · 性能与稳定性收口报告

> 范围：按 Gate 5 任务书执行——5,000 / 15,000 / 30,000 笔三档规模的**关键路径打点**、
> **与 v1.3.6 的逐项对照**、**7 类浪费逐条核查**。
> 本轮**不优化、不重写数据层、不跑 50k 压测**（任务书明确要求）。
>
> ⚠️ **口径先声明**：本报告所有数字都是 **Node 20+ + 内存文件系统**上的数据层 / 纯函数耗时，
> **不含**真机文件 I/O、`setData` 通信、WXML 渲染、Skyline/WebView 差异、图片解码。
> 它只能回答「同一环境下同一段代码谁快谁慢、有没有数量级退化」，**不能当"真机秒开"指标**。
> 详见 §八 限制说明。

## 二、环境与口径

| 项 | 值 |
|---|---|
| 机型 | AMD Ryzen 7 5800H（笔记本，未锁频） |
| OS | win32 10.0.26200 |
| Node | v22.22.2 |
| 文件系统 | 内存 FS（`Map`），**不触碰真实账本**；账本只存在于进程内存 |
| 数据来源 | `scripts/generate-realistic-ledger.js`（固定 seed=20261029、anchor=2026-10-29），虚构数据 |
| 取样 | 每路径每次运行取「3 次重复的中位数」；跨版本对照取「3 轮运行 → 轮内中位 → 多轮中位」（双中位数） |
| 执行方式 | 两版**交错执行**（A,B,A,B,A,B），避免"先跑的一版吃亏/占便宜" |

**为什么必须交错**：第一轮我先跑 3 轮 v1.4.0、再跑 3 轮 v1.3.6，结果**每一项都"更慢"20%~95%**（含纯函数）；
改成交错执行后符号立刻翻转（有的更快有的更慢），证明那是**机器冷热漂移**，不是代码差异。
这类噪声在本机约 **±20%~40%**，凡是绝对值 < 1ms 的项，百分比差异没有意义（下文统一标注）。

### 附：导入预览为什么是"超线性"（已定位，未修）

`packages/importer/core/dedupe.js:76-88` `findSuspect(b, existing)` 对**每一条新账单**做一次**全量线性扫描**
（`existing.some(...)`，无索引），`classify()`(:92-95) 每次还会 `store.rangeBills()` 全量读一遍账本。
代价 ≈ O(新账单数 × 账本条数)：

| 账本规模 | 3,000 行预览耗时 | 账本条数比 | 耗时比 |
|---|---|---|---|
| 5,000 | 220ms | 1× | 1× |
| 15,000 | 602ms | 3× | 2.7× |
| 30,000 | 3,039ms | 6× | **13.8×** |

耗时比 ≫ 条数比 ⇒ 超线性确认（30k 档实际已到 3 秒，**接近体验红线**）。
**这不是 v1.4.0 引入的**（`packages/importer` 两版零差异），属既有实现，登记在 §九③，本轮**未改动**。

## 七、稳定性观察（顺带核对，不属打点项）

- `App 冷启动自检` 在 30k 档 152ms，其中 `scanStorage()` 读满 85 个分片（约 7MB 文本）。
  这是 G6 数据保护模式的**设计代价**（启动即校验完整性），不是新问题。
- 三档规模全程**无异常抛出、无 unhandled rejection**；`restoreBackup` 造数 46~338ms 正常。
- 本轮改动（QA-01 隔离转存）位置在 `restore()` / `rollback()` 清空前，**只在恢复/回滚路径触发**，
  不在任何被测关键路径上。**实测其自身开销**（20,000 笔 / 73 分片、无损坏分片时）：
  **中位 26.8ms（24.1~29.9ms）** —— 代价是「按严格口径把每个月份分片再读+解析一遍」。
  对「用户主动点恢复」这种低频操作可接受；回滚只在失败时发生一次。
  若要压到接近 0，需要让 `buildBackup()` 顺带记录不可解析月份（同一遍扫描复用），
  那会改动安全点的数据形状，**超出本轮主线，本轮不做**（登记为 §九⑧）。

## 八、限制说明（不许当结论外推）

1. **无真机数据**：本轮无真机 / 开发者工具帧率、启动耗时、`setData` 往返、滚动 FPS。真机指标须另行真机 Gate
   （任务书未派，属 QG 边界）。
2. **内存 FS 偏乐观**：真实 `wx.getFileSystemManager()` 读 85 个分片远比内存 Map 慢，真机冷启动会明显高于 152ms。
   但**相对结论**（哪些路径全量扫、哪些只读单月）与真机一致，因为它由**读分片次数**决定，而非介质速度。
3. **绝对值仅供纵向比较**：同一台机器、同一进程模型下才有意义；换机、换 Node 版本会整体漂移。
4. **±20%~40% 噪声带**：绝对值 <1ms 或相对差 <15% 的项，一律不下结论（本报告已如此处理）。
5. 未做 50,000 笔（任务书明确不要求）；结论外推到 50k 需谨慎，但 §五 已确认主因是分片数而非账单数。

## 十一、结论

- **Gate 5 建议判定：通过（放行）**。无 v1.4.0 引入的退化；30k 极限规模下关键路径可接受；7 类浪费中 3 类未发现、
  4 类量级轻微且已量化登记。
- 唯一**用户可感知**的性能短板是「导入预览 3k 行 + 30k 账本 ≈ 3 秒」（既有实现，非本版引入），
  已登记为 **P2**（§九③），建议排进下一版而不是本版（本版主线是 Gate 6 收口，动它要重写去重索引，风险不对等）。
