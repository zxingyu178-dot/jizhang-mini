## B-1 主题（配色方案）扩展

- 客户原话：「我还感觉我们的主题比较少，添加到后续任务」
- 状态：**已做（1.4.5）**（按下方「落地建议」做了 A 方案：靛蓝 / 青竹 / 琥珀 / 玫红 4 套 × 深 / 浅，同步修掉 3 个存量缺陷；详见 `docs/HANDOFF_v1.4.5.md`）
  - **最终实现与方案 A 的差异**：`--glow-*` 也跟着色相走了（原方案 A 只打算保留靛蓝发光，实现时发现发光不跟色相会与主色打架；**客户已确认保留**）
- 现状：`settings.theme` 只有 `dark` / `light` / `system` 三种模式，本质是**两套配色**（深 / 浅）。`app.wxss` 已有 60+ 语义变量（`--bg` / `--surface` / `--card-bg` / `--primary` / `--expense` / `--income` / `--text-*` …），加配色的改造成本主要在**选色 + 对比度验证**，不在重构。

### 三个候选方向（成本递增）

| 方案 | 做什么 | 改动量 | 风险 |
|---|---|---|---|
| **A. 同一结构换强调色**（推荐先做） | 保持深/浅骨架不变，只覆盖约 15 个关键变量：`--primary` / `--primary-deep` / `--primary-glow` / `--glow-1` / `--glow-2` / `--hero-bg` / 分类色板。产出 3~4 套：靛蓝（现有）、青竹绿、琥珀、玫红 | 小（约 1~2 天） | 低：结构不动，只需逐套验对比度 |
| **B. 深色再分「夜色 / 纯黑」** | 深色主题下多一个 OLED 纯黑变体（`--bg: #000`），省电、讨好深色党 | 小（半天） | 中：纯黑下玻璃拟态的层次会塌，要重调 `--surface` / `--card-border` |
| **C. 完整换肤（换质感）** | 毛玻璃 / 扁平 / 拟物，三套不同视觉语言 | 大（1~2 周） | 高：每套都要重画卡片、图标、图表配色 |

### 参考案例（2026-11-10 调研）

**1. Copilot Money — 颜色带财务语义，不是纯装饰**
- 色板：Ledger Blue `#3A55D9`（账本）/ Night Balance `#141A33`（夜色）/ Budget Green `#2FB38A`（预算）/ Overdraft Coral `#E5675A`（超支）/ Paper `#FAFAF8`（纸）
- 借鉴点：**每套主题不该只是"换个主色"，而要有一套自己的语义色关系**。我们是记账 app，`--expense` / `--income` / `--budget-surplus` / `--budget-over` 这四个色在任何主题下都必须保持"一看就懂谁是支出谁是收入"
- 反面教训：**A 股/国内习惯是「红涨绿跌」，但记账语境里「支出=红、收入=绿」更符合直觉**——我们现在的实现正是 `--expense` 绿 `#3ddc8f` / `--income` 红 `#ff6b6b`，这是**反的**（支出绿、收入红）。若做主题扩展，建议顺手核对这个语义是否会让用户困惑
- 来源：https://madegooddesigns.com/copilot-money-brand-guidelines

**2. FinFlexi AI — 「一个暗底 + 多个情境强调色」**
- 做法：以 dark base 统一打底，不同页面/状态用 contextual accents（超支柔红、流入绿、AI 冷蓝）
- 借鉴点：**主题可以按"情境"分而不是按"皮肤"分**。比如「预算紧张时整个界面偏琥珀警示、正常时偏靛蓝」——比给用户 5 套皮肤更有产品意义，维护量也更小
- 来源：https://engineering.zooz.com/@ragesh-changam/finflexi-ai-a-premium-ui-system-for-gen-z-money-management-d5848f69d109

**3. 钱哪去了（国内独立开发）— 克制紫 + 蓝橙点缀**
- 主色 `#8D5CF4`，蓝与橙只做细节点缀，"轻盈、安静、不打扰"
- 借鉴点：**点缀色最多两种，且不参与大面积填充**。我们现在的靛蓝 `#7c86ff` 已经是这个路子，方向对
- 来源：https://pwa-test.sspai.com/post/103787

**4. 多主题设计系统的硬规则（通用最佳实践，必须遵守）**
- 深色**不是把浅色反转**：需要多个深灰层级（base / raised / overlay），靠"表面变亮"表达层级，而不是靠阴影
- 强调色在深色下要**降饱和 + 提亮**（同一 huen，只改明度与饱和度），否则会"发光刺眼"
- **纯黑 `#000` 不是好的深色底**：会增加眼睛疲劳（散光人群光晕），OLED 快速滚动还会有拖影；用 `#0B0D12`~`#161616` 更稳。我们现有 `--bg: #05060a` 已经很接近纯黑，做 B 方案时要谨慎
- 默认跟随系统 + 允许手动覆盖 + **记住选择**（我们已做到）
- 验收清单：WCAG AA（正文 4.5:1 / 大字号与图形 3:1）、色盲模拟（红绿型）、OLED 与 LCD 双测、禁用态与输入框边框也要验
- 来源：https://medium.muz.li/dark-mode-design-systems-a-complete-guide-to-patterns-tokens-and-hierarchy-79b3fce67823 ・ https://innovialabs.uz/en/blog/dark-mode-ui-design

### 落地建议（我的判断）
1. **先做 A 方案 3 套**（青竹 / 琥珀 / 玫红），因为它能验证「换色不炸布局」，成本最低、用户感知最直接
2. **不做 C 方案**（完整换肤），投入产出比最差
3. B 方案（纯黑）等 A 做完再看，因为纯黑会让现在的玻璃拟态卡片失去层次
4. 每套主题必须过 **对比度闸门**：正文 ≥4.5:1、图表刻度 ≥3:1（这次的 `--text-axis` 教训——刻度不该吃"可有可无"的灰）

**三条由实测得出的硬规则（下一轮实现必须遵守）**：
1. **按钮底按模式分**：深色主题用 `--primary`（亮色）+ **深色字**；浅色主题用 `--primary-deep`（暗一档）+ 白字。反着配必挂（实测亮色主色配白字只有 2.10~2.17）
2. **主色要分两层用**：`--primary` 只用于图形/边框/填充（≥3:1 即可），文字一律走 `--primary-text`（≥4.5）。原因：主色在全项目被当文字用 **16 处**，当背景只有 2 处
3. **`--on-primary` 不能写死白色**：青竹/琥珀这类亮色主色必须配深色字，否则按钮文字看不清

### ⚠️ 做主题前必须先修的 3 个存量缺陷（本次调研顺带发现）

| # | 缺陷 | 实测 | 影响 |
|---|---|---|---|
| 1 | **浅色主题主色当文字偏淡** | 靛蓝 `#6e78f5` on 卡片底 = **3.52**，正文标准 4.5 | 16 处 `color: var(--primary)` 全部受影响（选中项、链接、强调数字） |
| 2 | **深色主题按钮白字偏淡** | 白 on `#7c86ff` = **3.13**，按钮文字标准 4.5 | FAB、主按钮文字需改深色字 |
| 3 | **6 处 JS 硬编码主色，不跟主题走** | `components/category-icon/category-icon.js:18`、`components/icon/icon.js:16`、`components/daily-value-curve/daily-value-curve.js:18-23`（4 处折线色）、`data/statistics/cumulative.js:20` 的 `LINE_COLOR` | 换主题后图标高亮、首页日价曲线、统计页累计折线会**还是靛蓝**，出现"一半变色一半没变" |

> 缺陷 3 还有一个连带项：`scripts/theme-audit.js` 里的品牌色白名单（`#7c86ff` / `#6e78f5` / `#5b67f0` / `#5660e0` 及对应 rgba）是写死的，加主题后这个审计脚本会误报，需要改成按主题读。

## B-2 数据展示第二批优化

- 客户原话：「包括正在优化的数据展示板块」
- 状态：**部分已做（1.4.6）** —— 已做：标题写结论（4 张图标题下加结论行）、复查缩略（结论：明细金额本来就未缩略，只有坐标轴刻度用 `formatAxisAmount`，**无需改**）、同期环比上界面（Hero「本月支出」右侧）；未做：P2 参考线（**改为结论行文字表达，不在图上画线**）、P3 拆图（**不做**）
- 说明：v1.4.4 解决的是「看不清」（第一批），1.4.6 解决「看不快」（第二批：一眼读不出结论）

### 参考案例

**1. 一张图只回答一个问题**（Urban Geko）
- 原文要点：移动端屏幕寸土寸金，「每一像素的装饰都是从清晰度里偷走的」。一张金融图表**只回答一个问题**——消费节奏？储蓄进度？现金流趋势？不要一张图塞两个问题
- 落到我们：现在的「累计消费趋势」同时在说"花了多少"和"花得快不快"，可考虑拆成两张，或在图上加一条"按当前速度月末将达 ¥X"的参考虚线
- **重要提醒**：`$1,247` 不要为了好看缩成 `$1.2K`（精度重要时）。我们的 `万/亿` 缩略要复查一遍——**明细金额不缩，只有坐标轴刻度缩**
- 来源：https://www.urbangekodesign.com/?p=28571

**2. 标题要写结论，不写字段名**（PhonePe Design）
- 原文要点：不要叫「交易量」，要叫「XX 城市的 P2P 支付占主导」。**标题必须直接说出洞察**
- 坐标轴要**比数据点更淡**（muted），做参照不抢戏——**这条 v1.4.4 做对了**：`--text-axis` 比正文淡、网格线比刻度更淡
- 数字表达：一段话别超过 8 位数字；能用「三分之一」就别写「33.3%」
- 来源：https://design.phonepe.com/stories/design-x-data-storytelling

**3. Y 轴必须从 0 开始**（merge.rocks / SCT）
- 柱状图截断 Y 轴是"最古老的骗术"：从 $90k 起，$100k→$105k 看起来像翻倍
- **这条 v1.4.4 做对了**：三张图的底档都是 `0`
- 附带要求：**数字要有上下文**（对比上期 / 目标 / 平均值），否则"这个月花了 601"没有好坏判断
- 来源：https://merge.rocks/blog/fintech-dashboard-design-or-how-to-make-data-look-pretty

**4. 五秒测试**（merge.rocks）
- 拿给目标用户看 5 秒，问"这张图主要说什么"。答不出来就该简化
- 建议：下次真机验收时用这条做主观检查项

**5. 颜色不能是唯一编码**（PhonePe / 多篇）
- 色盲用户（红绿型约 8% 男性）分不清红绿。必须辅以符号、图案、虚线、文字
- 我们现状：分类有 emoji 图标 + 名称，**已经不只靠颜色**；但「收入/支出」目前只靠红绿区分，可考虑加 `+` / `-` 符号（账单列表已有 `-`，基本够）

### 落地建议（优先级）
| 优先级 | 做什么 | 理由 |
|---|---|---|
| P1 | 图表标题写结论（如「本月日均 ¥20，比上月少 12%」） | 客户要"清晰明了"，结论式标题最直接 |
| P1 | 复查「万/亿」缩略是否用到了明细金额上 | 精度不能为美观让步 |
| P2 | 给累计图加"按当前速度月末将达 ¥X"参考线 | 把"花了多少"升级为"会不会超" |
| P2 | 增加环比/同比对比（哪怕只是一行小字） | 单个数字没有好坏，有对比才有判断 |
| P3 | 累计图拆分（花多少 / 花多快） | 一张图回答两个问题，违反单一职责 |
